# power018：原厂电池与适配器认证

沿已验017的SC8585 ADC和驱动PM、GPU015/USB829继续。018目前完成源码和必要宿主验证，尚未原生构建或实机验证。

当前OS4的`batterysecret`对nezha选择FG密钥2：`C2CC=2`经`57d4→536c`及`80a8`重定位取`C038`的32字节密钥。它不等于公开脚本的两套FG回退密钥。适配器SEEDS160B/KEYS320B逐字节与已固定公开参考一致。认证材料只由本机原厂文件生成，作为本地候选的528B设备树属性`/chosen/nezha-power-auth-material`传入；不放入源代码、CI上传或诊断输出。属性存在且格式正确时启用，也支持显式`nezha-power-auth=0`关闭；实际默认启动参数保持原长度。

## 同一worker的流程

1. 在新鲜有线PD/type10和新的MCA epoch/attachment下读取SVID、Adapter ID、verify_process。只接`2717`，已有认证过程不接管；同次附件失败不循环重发。
2. 现有唯一`0x55`gauge的易失MAC0认证：`3E`写入命令0、32B随机挑战、校验和及`24h`长度，总36B；原厂等待400ms后从`40`读取32B摘要。原有GPI/时钟/DMA资源和单worker保持，正常睡眠等待由`IOSleep`提供。内核既有`cchmac/ccsha256_di/read_random`完成比较；不新增加密provider。
3. 用原厂合法`0x2100b`设置/读回PD verified=0，`0x21002`设置/读回verify_process=1。随后按nezha原顺序执行VDM `1,2,3,4,5,7,6`；初始254对应的同一verified属性由明确清0/读0替代原厂`null`字符串解析。
4. 种子/挑战在MCA上每4B翻转，回应按同一字序还原。计算`HMAC-SHA256(key32, challenge16 || AdapterID_BE4)`，比较摘要前16B。正确结果才发送认证/补偿真值、设置并新鲜读回PD verified；最后清verify_process并新鲜读回。写ACK和实际认证结果分别记录。
5. 正常停止、驱动休眠、源或远端改变均立即撤销公布的认证结果，必要时经同一worker清理本方verified/process状态并读回。每个已接受的清0请求只发送一次，随后在原期限内只读观察；超时仍保留未知所有权并阻止PM完成。停止后拒绝尚未发出的新认证写，只保留必要清0。恢复依赖原MCA新epoch，沿既有驱动PM流程。

认证只使用原MCA收发和板级所有者。provider9新增状态、错误、实际附件及认证结果；`A2`只含状态/结果/错误码，挑战、摘要和密钥不进入A1原始日志或USB控制输出。认证完成后刷新type/PDO/verify元数据，避免沿用认证前的能力。

## 资格与验收

宿主覆盖15项认证核心、4项易失MAC、5项真实runtime/MCA调用，以及32项旧充电/驱动PM回归、CPU无效样本撤下、诊断有界JSON与旧/新日志CRC计数。新回归实际覆盖原VDM期限之外的迟到读数、清0已接受后只读等待及超时所有权、停止时排队的新认证写拒绝，以及日志暂忙恢复后同一尚未发送的挑战只发送一次。它们只证明受测代码路径，不能当硬件认证通过。

下一步唯一Native018必须携带新Auth/Native/MAC/状态符号，并保留原全部14项严格/GPU015/USB/固件/PAC/17/读取器/8CPU资格。本地封包另核528B材料的实际ADT内容及固定SHA；原厂材料不上传。只有完整资格和真实空闲窗口后才按现有授权原27payload范围、临时boot测试。

真机先证当前provider9、独立本方日志、正确的认证材料启用状态，再接原厂充电器和原厂线。同次观察主gauge真实摘要通过、VDM/HMAC通过、新鲜verified/process读回，以及认证后实际type/PDO改变。返回PC检查新USB会话；一次正常XNU返回、必要Android/root后验、停自有采集与有界日志CRC后立即释放。

018尚未加入PPS电压调节、充电泵使能、完整JEITA/FFC或90W执行后端，也没有原厂认证实测。009读取、013普通充电控制、017 ADC/本方PM保持各自实测身份；不以018准备或编译通过升级高压/快充或主包。原厂9V/1500mA/恢复5V可继续用固定017补验，其试验要求SOC低于95%，充入量只按详细日志连续180秒。
